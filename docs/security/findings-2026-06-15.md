> **Method:** multi-agent static/manual attack-surface survey across all six
> trust boundaries, followed by independent re-verification of every HIGH

> findings**, not weaponized exploits. "Repro: code-confirmed" means the

## HIGH

### F-01 — Inverted egress is an unauthenticated SSRF-capable proxy under the default AllowAll policy — **SSRF half CLOSED (PR #32); posture half is a product decision**
- **Status (2026-07-21):** the SSRF-capable half is **fixed**. An
  `is_hard_denied` floor (loopback/link-local/metadata/unspecified) now runs
  **before any policy**, including the AllowAll path — `router.rs` (see
  `decide_tier2_bare_hard_denies_loopback_and_metadata`), so a bare sandbox can
  no longer be steered at `127.0.0.1`/`169.254.169.254`/LAN. The **default is
  still AllowAll for public hosts** — that is the deliberate "bare sandbox =
  allow-all until a policy is declared" decision (roadmap decisions log), not a
  bug; the fail-closed principle governs *enforcement degradation*, not the
  opt-in baseline. Making default-deny the baseline remains a possible future
  product change, not an open finding.
- **Boundary:** B3 (guest→izbad egress). **Repro (original):** code-confirmed (router.rs:56-145).
- A bare/M1 sandbox runs `AllowAll` (non-enforcing). `decide_tier2` returns
  Allow for **any** raw IP — the `is_private` guard at router.rs:263 is applied
  *only* when `policy.enforces()`. The hostile guest sends
  `StreamOpen::TcpConnect{addr,port}` and izbad dials it **from the host's
  network namespace** — `127.0.0.1:*`, LAN, cloud metadata `169.254.169.254`.
  The dummy0/nft "deny" only constrains the guest's own datapath; the proxy
  runs on the host. There is no default-deny unless a `--policy` is attached.
- **Fix:** apply the private/loopback/link-local/metadata denylist
  **unconditionally** (independent of `enforces()`); make default-deny the
  baseline posture for *all* sandboxes, with AllowAll an explicit opt-in.

### F-USB-1 — A sandbox can reach a usbip upstream over the generic egress plane, bypassing the USB device allowlist — **CLOSED (USB phase 1)**
- **Status (2026-08-04):** **fixed** by the `usbip_guard` floor in `router.rs`,
  landed ahead of any USB datapath so the bypass can never be live. Pinned by
  `enforcing_sandbox_cannot_reach_usbip_port_even_if_policy_lists_it`,
  `usb_enabled_bare_sandbox_cannot_reach_usbip_port`, and
  `configured_upstream_endpoint_is_denied_on_its_own_port`.
- **Boundary:** B3 (guest→izbad egress). **Repro:** code-confirmed.
- The guest's nft ruleset REDIRECTs all non-53 TCP into the egress stub
  (`izba-init/src/egress.rs`), so an in-guest `usbip attach -r <ip>` is
  mechanically an ordinary `StreamOpen::TcpConnect`. The `is_hard_denied` floor
  covers loopback/link-local/metadata but **not RFC1918** — that is policy-
  governed, and a bare sandbox is permissive for LAN by design. In WSL2 NAT
  mode the Windows host *is* an RFC1918 gateway, and usbipd-win's installer
  opens TCP 3240 to **all local subnets** by default. An enforcing sandbox was
  also exposed whenever its policy listed an IP that happened to run usbipd.
  Either way the device would be imported without ever passing the per-device
  allowlist izbad enforces on the USB plane.
- **Fix (revised 2026-08-04 after product review):** deny TCP 3240 and the
  configured upstream endpoint — by port *and* by canonicalised address, since
  one usbipd is reachable at several spellings at once — for a **bare,
  USB-enabled** sandbox. Checked before the tier-1 MITM branch so an upstream on
  an HTTP(S) port cannot reach the MITM hop instead.
- **Governing principle:** *this default may fill in where the user expressed no
  decision; it must never veto one they made.* An **enforcing** sandbox is
  already default-deny, so a usbip check there would add nothing except
  overriding an explicit rule — and opening 3240 cannot happen by accident,
  since a bare host entry authorizes only `[80, 443]`
  (`AllowEntry::DEFAULT_PORTS`), so the user must literally write
  `ports: [3240]` against a named host. That rule is **honored**; the user is
  warned when they write it (`usbip_exposure_warning`), pointing them at the
  per-device allowlist as the narrower, recommended grant.
- **This is deliberately weaker than the `is_hard_denied` SSRF floor.** Those
  targets are non-overridable because they are *confused-deputy* targets —
  dangerous precisely because izbad dials them from the HOST's network position,
  letting the guest reach what it structurally could not reach itself. A usbip
  server on a LAN address is an ordinary external destination the user is naming
  on purpose, and does not warrant the same veto.
- **Honest limits.** (a) It is a default, not a boundary: a usbipd on an
  unconfigured non-3240 port is not matched. (b) The earlier claim that this
  bypass is "inert without `vhci-hcd`" was **wrong and has been withdrawn** —
  `vhci-hcd` is a convenience that makes the device appear as a real USB device;
  the USB/IP protocol is fully usable from userspace (izba is itself writing a
  userspace client), so an agent in any sandbox can import a device and drive
  URBs over plain TCP with no kernel support. The **bare, non-USB** carve-out
  (LAN access on 3240 retained) therefore rests solely on the product decision
  that a bare sandbox is permissive by design, not on any structural inability.
- **Phase 2 (2026-08-05):** the guard is no longer a floor with a defaulted
  input. `usb::guard_for` resolves `sandbox_usb_enabled` from the sandbox's real
  device grants and `upstream` from the configured endpoint, and
  `EgressManager::apply_usb_guard` keeps both live across grant/revoke (mirroring
  `apply_policy`). So the first grant closes the LAN path to the upstream on the
  sandbox's **next flow**, not at its next restart — and revoking the last grant
  reopens it, rather than leaving a denial the sandbox no longer earns. Pinned by
  `apply_usb_guard_swaps_a_live_slot` and the `guard_for` tests.

### F-USB-4 — The usbip upstream is unauthenticated and unencrypted — **MITIGATED (USB phase 2)**
- **Status (2026-08-05):** mitigated by `usb::trust`. A globally-routable
  upstream is **refused outright** unless the operator passes `--allow-remote`,
  and every non-loopback class carries a warning naming the address and stating
  that anyone who can route there can attach the same devices and can read or
  modify the traffic. Opting in silences the refusal, never the warning.
- **Boundary:** B-USB (izbad→upstream). **Repro:** n/a (design property).
- The naive test — "warn unless 127.0.0.1" — would be actively wrong on izba's
  primary platform: under WSL2 NAT the user's own Windows host is an RFC1918
  default gateway, so conflating it with a third-party LAN box would make the
  loud warning routine and therefore ignored. `classify` separates the two using
  `/proc/net/route` (**never** `resolv.conf`, which under izba's DNS tunnelling
  names a stub address, not the host) plus a WSL check. Both inputs are injected,
  so the classifier is pure and fully unit-tested; when either is unavailable the
  code falls back to the *more* restrictive class, never the less.
- An upstream host that does not resolve classifies as `Public` — the most
  restricted class, not the safest-sounding one. izba does not know whose machine
  it is, so it does not grant it the benefit of the doubt.
- **Residual:** the classification is of the *address*, not of the party
  answering on it. It tells the user who they are choosing to trust; it cannot
  verify that the answering server is the one they meant.

### F-USB-2 — Passthrough gives a hostile guest a byte channel into a privileged host service — **MITIGATED, RESIDUAL ACCEPTED (USB phase 3)**
- **Status (2026-08-06):** the datapath now exists, so this is live rather than
  prospective. Four controls stand between a guest and `usbipd`:
  **(a)** the plane is bound only for a sandbox that already holds a human-issued
  grant *and* has a configured upstream — with USB off there is no socket to
  dial, not a listener that would refuse;
  **(b)** the guest never speaks USB/IP: it sends one `vid:pid` label and izbad
  performs the whole op phase itself, so the guest supplies no address, no
  busid, and no protocol bytes during negotiation (D1);
  **(c)** every guest→upstream URB header is validated
  (`usb::broker::session::pump_guest_to_upstream`, over the phase-1
  `decode_guest_urb`) — a reply command, an out-of-range endpoint or direction,
  an oversized transfer or an absurd isochronous count all stop the stream
  rather than being forwarded, and the stream is NOT resynchronised afterwards,
  because the bytes following a refused header are the rest of a message izba
  declined to understand;
  **(d)** the handshake is deadlined, so a guest that dials and says nothing
  cannot hold a thread or a claim on hardware.
- **Boundary:** B-USB (guest→izbad→upstream). **Repro:** n/a (design property).
- **Residual, accepted:** validation is *hygiene and framing*, never
  authorization. A well-formed URB carrying a hostile payload to a device the
  human granted is indistinguishable from a legitimate one, and izba forwards
  it — that is what granting a device means. The boundary is the grant, not the
  byte stream.
- Fuzzed continuously: `crates/izba-core/fuzz/fuzz_targets/usbip_pump.rs`.

### F-USB-3 — Device identity is upstream-asserted; `vid:pid` is not proof of provenance — **MITIGATED (USB phase 3)**
- **Status (2026-08-06):** the USB/IP wire format carries **no serial number**
  (it is a string descriptor, fetched separately), `vid:pid` is
  device-programmable, and a busid is recycled across a replug. izba therefore
  treats the allow-list as an expression of human *intent* and says so verbatim
  in the consent banner and the README.
- What is enforced: the `vid:pid` is resolved to a busid at **attach** time from
  a fresh `OP_REQ_DEVLIST` (never cached), the import is re-verified against the
  grant after `OP_REP_IMPORT` (`session::verify` — an upstream that returns a
  different device is refused before the guest's kernel sees it), and a
  `--busid` pin is honored **only** while the device on that port still matches
  the granted `vid:pid`, so a pin can never be the sole basis for an attach.
- Two identical devices are refused as ambiguous rather than resolved by
  picking: silently choosing one would attach hardware the human never pointed
  at, and they would have no way to tell which.
- **Boundary:** B-USB. **Repro:** n/a (protocol property).
- **Residual:** a device that lies about its `vid:pid`, or an upstream that lies
  about both, is indistinguishable from the real one. Closing this needs a
  `GET_DESCRIPTOR` serial probe, deferred to v1.1 behind an explicit `serial:`
  grant entry (spec §9).

### F-USB-5 — A hostile or MITM'd upstream attacks the guest USB stack — **ACCEPTED (USB phase 3)**
- **Status (2026-08-06):** the upstream→guest direction is spliced **opaquely**
  and deliberately: its victim is a guest kernel already assumed hostile under
  A1, so parsing it buys no protection while adding a stateful parser to the hot
  path (`RET_SUBMIT` zeroes direction and endpoint, so framing replies would
  require tracking seqnum→direction for every in-flight request). Reasoned in
  full at `izba_proto::usbip::urb`'s module doc (design D6).
- **Boundary:** B-USB (upstream→guest). **Repro:** n/a (accepted by design).
- Guest compromise is not a sandbox escape under A1, but it is not free either:
  it costs `/workspace` confidentiality and hands a third party a stronger
  position from which to attempt a virtio escape. That is precisely why F-USB-4's
  classification names *whose machine* is being trusted rather than merely
  warning that the link is unencrypted.
- Reduced, not eliminated, by the kernel variant: a USB-capable kernel reaches
  only sandboxes whose owner granted a device, and it carries only the serial
  drivers (cf. F-USB-6), so the exposed attack surface is CDC-ACM plus four
  USB-serial bridges rather than the whole USB subsystem.

### F-USB-6 — A USB-capable kernel would ship to every sandbox — **CLOSED (USB phase 3)**
- **Status (2026-08-06):** **closed** by the kernel variant (design D4).
  `hack/kernel.config` disables `CONFIG_USB_SUPPORT` outright, and
  `hack/kernel-usb.config` re-enables it *only* for the separate `vmlinux-usb`
  artifact, which `artifacts::locate` selects solely from the sandbox's grants.
  A sandbox without grants boots a kernel with no USB stack — nothing to attach
  to, nothing to exploit.
- The variant fails **closed**: a USB-granted sandbox whose installation lacks
  `vmlinux-usb` refuses to start with an actionable error rather than falling
  back to the base kernel, which would boot, accept an attach, and silently have
  no device. `IZBA_KERNEL_USB` is a separate override from `IZBA_KERNEL` so an
  e2e meant to exercise the USB kernel cannot pass on the base one.
- The variant also turns the **physical** host-controller drivers back off
  (xHCI/EHCI/OHCI/UHCI): neither Cloud Hypervisor nor OpenVMM emulates a USB
  controller, so they could never bind to anything. "USB kernel" means exactly
  one controller — the virtual one izba drives over vsock.
- **Boundary:** B-USB / guest kernel. **Repro:** covered by the e2e assertion
  that a grantless sandbox has no `vhci` in `/sys/devices/platform`.

### F-02 — MITM never checks ClientHello SNI == HTTP Host (allow-list bypass / domain fronting) — **CLOSED (PR #32)**
- **Status (2026-07-21):** **fixed** in the hyper-util MITM rebuild. `serve_mitm`
  binds the policy verdict, the upstream TLS server-name, and the audited host
  together; SNI is reconciled to the HTTP Host, a Host/authority mismatch is
  rejected (403), and the upstream cert is verified via webpki against the
  vetted Host (`mitm.rs`, `serve_mitm` + the `403 … authority/Host mismatch` /
  `SNI/Host mismatch` deny paths). Domain-fronting via SNI≠Host no longer
  passes policy.
- **Boundary:** B5. **Repro (original):** code-confirmed (mitm.rs:233 leaf-by-SNI;
  mitm.rs:401-408,461,479 policy/upstream-by-Host; mitm_runtime.rs:230 dial-by-OrigDst).
- The leaf is minted for the **ClientHello SNI**; the policy verdict, the
  upstream TLS server-name, and the audited host are taken from the **decrypted
  HTTP Host header**. Nothing asserts SNI == Host. The upstream socket is dialed
  at the guest-chosen `OrigDst` IP while the cert is verified against `Host`.
  A guest can present `SNI=anything`, `Host=allowed.example.com`, `OrigDst=` an
  IP that serves a valid cert for the allowed Host — passing policy while izbad
  TCP-connects where the guest chose.
- **Fix:** require SNI == Host (or reconcile + re-verify); pin the upstream dial
  to the policy-approved name's resolved address, not guest `OrigDst`.

### F-03 — Only the first HTTP request on a kept-alive MITM connection is policy-checked — **CLOSED (PR #32)**
- **Status (2026-07-21):** **fixed**. The hyper-util stack runs a per-request
  policy `Service`, so every request on a kept-alive connection is
  re-classified and a second Host can no longer be smuggled past the first
  check. Regression test `keepalive_second_request_is_rechecked` (`mitm.rs`)
  pins it; multi-Host and confused-deputy Host rewrites are rejected.
- **Boundary:** B5. **Repro (original):** code-confirmed (mitm.rs:458-488).
- `read_request_head` runs **exactly once**; after Allow, `pump_bidirectional`
  copies all remaining bytes verbatim. HTTP/1.1 keep-alive lets the guest send
  `GET allowed.com` to pass, then reuse the same TLS+TCP session for requests
  with arbitrary `Host`/path. The audit log records only the first request, so
  `izba netlog` systematically under-reports.
- **Fix:** parse and policy-check **every** request on the connection (full
  HTTP/1.1 framing), or disable keep-alive (force `Connection: close`) so one
  connection = one checked request.

### F-06 — VMM and virtiofsd run unjailed/unconfined as the full host user
- **Boundary:** A2 (containment). **Repro:** code-confirmed (cloud_hypervisor.rs:131
  via `spawn_detached`; procmgr/unix.rs:23).
- cloud-hypervisor, openvmm and virtiofsd are launched with **no user/namespace
  drop, no seccomp, no chroot, no resource jail** — unlike Firecracker's jailer.
  A VM-escape (B-VIRTIO) or virtiofs bug therefore yields the **invoking host
  user's** full privileges. For a product whose purpose is sandboxing, the
  host-side VM process is the last line of defense and it is unconfined.
- **Fix:** a jailer-equivalent per sandbox: dedicated uid/gid, mount + pid + net
  namespaces, a seccomp profile, cgroup limits; minimally, drop privileges and
  seccomp-confine the VMM and virtiofsd processes.
- **Status update (2026-06-16) — Windows VMM: MITIGATED** (branch/PR
  `windows-vmm-jailer`; spec
  [docs/superpowers/specs/2026-06-16-windows-vmm-jailer-design.md](../superpowers/specs/2026-06-16-windows-vmm-jailer-design.md),
  plan
  [docs/superpowers/plans/2026-06-16-windows-vmm-jailer.md](../superpowers/plans/2026-06-16-windows-vmm-jailer.md)).
  The OpenVMM process now launches **confined by default**: a restricted token
  (`DISABLE_MAX_PRIVILEGE`, all privileges dropped) + **Low integrity** + a
  best-effort resource job (no kill-on-close) + creation-time process
  mitigations. It **fails closed** (errors rather than running unconfined)
  unless the user passes `--allow-unconfined` (which warns loudly); `izba status
  NAME` reports the confinement honestly. Proven in the `windows-whp` e2e via a
  differential `confine_probe` PoC + a live-status assertion.
- **Workspace integrity model:** the confined VMM runs at Low IL, so MIC
  no-write-up means it can only write Low-or-below objects. izba therefore
  Low-labels exactly the surface the VMM must write — the per-sandbox scratch dir
  (console.log/rw.img/vsock) **and** the virtiofs workspace share (the user's
  project dir; the guest writes `/workspace` through the VMM's in-process
  virtiofs). The label is inheritable and **probe-proven** to propagate to
  plain-created children, and is **restored to ~Medium on teardown** (graceful
  stop, force-remove, the daemon-adoption stale-state sweep that reconciles
  orphaned VMMs, AND the launch error paths — since relabel precedes state.json, a
  failed confined start is restored explicitly so the user's dir is never stranded
  at Low). A missed restore is benign (Medium tools write *down* to a Low dir
  freely). Everything *outside* the shared workspace stays Medium and so is
  no-write-up-protected from the Low-IL VMM — that is the integrity boundary.
  **Accepted residuals of integrity-relabelling** (all benign for the boundary,
  surfaced by adversarial review, code-documented; each closed by the
  dedicated-account hardening tier which never relabels the user's dir): restore
  is approximate (re-asserts explicit Medium, not the exact prior SACL);
  atomic-rename-in saves from outside the tree keep a non-Low label the guest
  can't write (narrow); VMM-created files keep their explicit Low label after
  teardown (workspace left with some Low files); and teardown keys on the tracked
  parent pid, so an untracked surviving `openvmm vm` worker is a pre-existing
  liveness gap.
- **Accepted residual (live-validated 2026-06-16):** **no read-confinement on
  Windows.** Restricting-SID shaping is infeasible for this single-token model
  (process init fails `0xC0000142`, even native cmd.exe; Chromium's two-token
  warmup is unavailable to a third-party VMM). The token therefore gives
  **integrity** protection (no write-up to the user's files, no privilege
  escalation, resource-capped) but a Low-IL VMM **can still
  read** the user's files outside the share. (Child-process creation is **not**
  blocked — OpenVMM forks a worker and the Windows primitive is all-or-nothing;
  children inherit the restricted token + Low IL, so they are deprivileged but
  not prevented from spawning.) Read-confinement needs a **distinct principal**:
  AppContainer (probe-proven to break WHP → ruled out) or a **dedicated
  low-privilege local account** for the VMM (one-time admin). The latter is the
  documented **future hardening tier** (`izba install --harden`): run the VMM as
  an `izba-vmm` account in Hyper-V Administrators with the workspace ACL-granted
  per run → read **and** write confinement, closing this residual (and removing
  the workspace integrity-relabel). Probe-gated on (i) WHP under a separate
  account and (ii) cross-account ACL plumbing. **Accepted for now** (integrity
  floor shipped; account ceiling documented) — rationale in
  [windows-vmm-jailer-chromium-reference.md](windows-vmm-jailer-chromium-reference.md)
  and the spec above.
- **Status update (2026-06-18) — Linux VMM: MITIGATED** (branch/PR
  `linux-vmm-confinement`; spec
  [docs/superpowers/specs/2026-06-18-linux-vmm-confinement-design.md](../superpowers/specs/2026-06-18-linux-vmm-confinement-design.md)).
  cloud-hypervisor and virtiofsd now launch **confined by default** on Linux:
  explicit `--seccomp true` (CH built-in), `--landlock` (CH built-in, Landlock
  v5+), virtiofsd `--sandbox namespace` (fallback `chroot` when userns is
  unavailable), and best-effort `setrlimit` (RLIMIT_NOFILE/NPROC) applied at
  spawn. Launch **fails closed** if the floor (seccomp + Landlock + virtiofsd
  sandbox) cannot be met, unless `--allow-unconfined` is passed (which warns
  loudly). Achieved confinement mode is recorded in `state.json` and surfaced
  by `izba status`. Per-sandbox uid jailer (full namespace isolation) is deferred
  to the userns-jailer follow-up, tracked as **F-29**.

### F-07 — virtiofsd launched with `--sandbox none` — **CLOSED**
- **Boundary:** B4 / A2. **Repro:** code-confirmed (cloud_hypervisor.rs:62-64).
- virtiofsd — the component directly parsing guest FUSE requests against the
  shared host dir (which **is the user's real project directory**) — is started
  with `--sandbox none`, disabling its own namespace + seccomp self-confinement.
  A path-traversal/symlink or memory bug in virtiofsd then operates with the
  full host-user filesystem view (cf. Kata CVE-2026-47243).
- **Fix:** `--sandbox chroot` (or run virtiofsd inside a user namespace);
  combine with F-06 so a virtiofsd compromise is contained regardless.
- **Closed by MVP-C (2026-06-18):** `--sandbox none` is replaced by
  `--sandbox namespace` (preferred; requires unprivileged user namespaces) with
  automatic fallback to `--sandbox chroot`. The sandbox mode is selected at
  launch time via `Capabilities::probe().userns`; launch **fails closed** if
  neither is available (treated as floor violation alongside seccomp + Landlock).
  See F-06 Linux status update and
  [docs/superpowers/specs/2026-06-18-linux-vmm-confinement-design.md](../superpowers/specs/2026-06-18-linux-vmm-confinement-design.md).

### F-08 — Host-side `cp` unpack of a guest tar has no openat2 confinement (guest→host arbitrary write)
- **Boundary:** B-CP. **Repro:** code-confirmed (cp.rs:119-149).
- `copy_from_guest` unpacks an **untrusted guest-produced** archive with
  `entry.unpack(&dest_path)` + `create_dir_all(parent)`, trusting the `tar`
  crate alone. The guest-side receiver (`izba-init/tarfs.rs`) is carefully
  hardened (openat2 `RESOLVE_IN_ROOT`, lexical `..` rejection, final-symlink
  replacement) — the host side has **none** of that. `rewrite_top` rewrites only
  the first path component, so traversal components later in an entry name pass
  through the join; the classic two-step symlink escape (entry A = symlink
  `x → /tmp/evil` or `../../..`, entry B = file `x/payload`) depends entirely on
  the exact `tar` 0.4.x hardening with no second line of defense. This is the
  highest-value lead: the guest is the attacker and the write lands on the host.
- **Fix:** mirror the guest-side hardening on the host — openat2
  `RESOLVE_IN_ROOT` / `O_NOFOLLOW` per entry, reject `..`/absolute, refuse to
  follow symlinks during extraction; add a differential test against tarfs.rs.

### F-32 — Docker mode's `readonlyPaths` is defeatable; container→guest-root containment rests on the rootless uid invariant — **CLOSED (invariant by construction since the 2026-08-09 shifted map; originally fail-closed, #198); RESIDUAL: docker mode is strictly weaker than builder/privileged**
- **Boundary:** container→guest (in-VM), and thence egress-governance. **Repro:**
  real-VM probe, `docker_mode_engine_runs_containers` phase [5c].
- Docker mode (#198) grants the workload container userns `CAP_SYS_ADMIN`
  (dockerd + nested runc need it) and applies **no OCI seccomp profile**. The
  narrowed `/proc/sys` read-only remount (`DOCKER_READONLY_PROC_SYS`, keeping
  every non-`net` sysctl RO) is therefore **defense-in-depth only, not a
  barrier**: `readonlyPaths`/`maskedPaths` are self-created mounts in the
  container's own mount namespace and are **not `MNT_LOCKED`**, so a
  `CAP_SYS_ADMIN` holder `mount -o remount,rw /proc/sys/kernel` (or bind-remounts,
  or mounts a fresh `procfs`) and the RO is gone. **Proven on a real VM** — the
  remount returns 0; the write error transitions EROFS→EACCES. This matches the
  documented rootless-container reality: readonlyPaths/maskedPaths are best-effort
  everywhere.
- **Why it is nonetheless contained (the real control):** the durable barrier is
  the **container-0 ≠ guest-0 uid invariant**, exactly as in rootless
  Docker/Podman. A non-`net` sysctl write (the file owned by guest-uid-0) is
  gated by `sysctl_perm`/`test_perm` — a plain `current_euid() ==
  GLOBAL_ROOT_UID` DAC check — so when container-root maps to a NON-zero guest
  uid the acting euid is not guest-0 and the write is denied. `CAP_DAC_OVERRIDE`
  cannot bypass it either: `capable_wrt_inode_uidgid` (torvalds/linux
  `23adbe12`) additionally requires the file-owner uid to be **mapped into the
  acting userns**, which a container-0 ≠ guest-0 map leaves unmapped. So the
  write is denied *regardless of any remount* (verified: `core_pattern` write
  EACCES, value unchanged, under `remount,rw`).
  **2026-08-09 update (uid-fidelity redesign,
  `2026-08-09-docker-uid-fidelity-design.md`):** docker mode no longer uses
  `transpose_identity_map` (which could break the invariant — container-0 →
  guest-0 — for a root-owned workspace, `workload == owner`, or a non-root
  image `USER` on a non-root workspace, and then required a fail-closed start
  refusal). `docker_shifted_map` satisfies the invariant **by construction**
  for every (owner, USER) shape — container-0 → guest `BASE` (or the non-zero
  owner) — and is **strictly stronger**: guest-uid-0 is now entirely UNMAPPED
  in the container userns (the old transpose mapped it to the workload id,
  keeping `capable_wrt_inode_uidgid` satisfiable for guest-root-owned inodes).
  The image-fidelity half (idmapped erofs/ext4 layers, same extents) changes
  only how DISK ids present; the userns barrier is unchanged in kind.
  `docker_userns_isolates_root` remains as a `generate_spec` regression
  tripwire over the actual mappings, and e2e phase [5c] still proves the
  denial on a real VM.
- **Sources (rootless alignment):** rootlesscontaine.rs/how-it-works/userns;
  github.com/containers/podman/discussions/16558 (uid 0 unmapped ⇒ /proc,/sys
  show as `nobody`); man7 `user_namespaces(7)` "Operation of file-related
  capabilities"; torvalds/linux `23adbe12` (`inode_capable`→
  `capable_wrt_inode_uidgid`); docker.com/engine/security/rootless/uid-gid-mapping
  (container-0 → host unprivileged user, never host 0); runc GHSA-9493-h29p-rfm2;
  kinvolk.io/blog/2018/04/towards-unprivileged-container-builds.
- **Residual (accepted):** docker mode is **strictly weaker** than izba's shipped
  builder/`privileged` mode reasoning would suggest at a glance — it deliberately
  hands the workload `CAP_SYS_ADMIN` with seccomp off inside a userns. A hostile
  workload that reaches container-root (allowed only under the safe uid map) is
  still confined by (a) the uid invariant above, (b) the **microVM boundary**
  from the host, and (c) the **NIC-less structural egress deny** — the guest has
  no route out except the izbad-governed vsock plane, and the workload's own netns
  reaches it only through the nat prerouting REDIRECT, so even a guest-root
  process cannot exfiltrate off-box outside policy without also defeating the VMM.
  Not closed: a `--docker` sandbox is a larger in-VM attack surface than a normal
  least-privilege sandbox; treat docker mode as "root-in-a-throwaway-VM", not as
  a hardened container.
- **Enforced/pinned by:** `docker_userns_isolates_root` +
  `docker_start_fails_closed_when_container_root_would_be_guest_root` (host unit),
  and `docker_mode_engine_runs_containers` phase [5c] (real-VM: remount allowed,
  `core_pattern` write DENIED, value unchanged) + [5d] (user-owned `/workspace`
  stays writable, so the invariant does not break the product).

## MEDIUM

### F-04 — Egress audit log: no integrity protection, lossy, under-reports
- **Repro:** code-confirmed (audit.rs:185-201). Plaintext JSONL, append,
  **all write errors silently swallowed**, no hash-chain/fsync; host-writable.
  Combined with F-03 it under-reports what a hostile guest actually sent. Audit
  is observability, not a control. **Fix:** append-only + hash-chain (or signed)
  records; surface write failures; log every checked request.

### F-05 — DNS-snoop trusts attacker-influenced answers as the tier-2 allow-list key; DNS forwarder is an open exfil channel — **escalated to P1 backlog #148 (2026-07-21)**
- **Status (2026-07-21):** confirmed still open and escalated. The
  enforcement-gap half (DNS has no enforcement tier even for an enforcing
  sandbox — an open QNAME exfil/C2 channel) is now tracked as **P1 backlog
  issue [#148](https://github.com/Lupus/izba/issues/148)**, at the top of the
  queue. The remediation there (resolve allow-listed names in izbad + deny
  unknown QNAMEs for enforcing sandboxes) also closes the rebind-priming half.
- **Repro:** code-confirmed (router.rs:70-76 port-53 short-circuit *before any
  policy*; dns_snoop.rs:36-57; router.rs:226-307 decide_tier2). All DNS (UDP +
  TCP:53) is unconditionally forwarded to the host resolver, even for an
  enforcing sandbox — a covert C2/exfil side-channel (data in QNAMEs) with no
  rate limit. `extract_a_aaaa` then records `(allowed-name → resolved-IP)` from
  guest-chosen queries; a guest that influences resolution (own domain / low-TTL
  rebind) can plant `allowed-name → attacker-IP` and dial it on a non-HTTP port
  to pass tier-2. The 60 s TTL floor *widens* the rebinding window.
  **Fix:** subject DNS to per-sandbox policy + rate limits; do not treat snoop
  data as authorization (it is a heuristic — threat-model §8); for enforcing
  sandboxes resolve allow-listed names *in izbad* and pin dials to that result.

### F-09 — izbad control socket has no authentication or peer-credential check — **CLOSED on Linux (M5 P0); RESIDUAL: Windows AF_UNIX has no uid-equivalent peer credential**
- **Fixed:** the accept loop authenticates the peer via `SO_PEERCRED` before
  spawning a handler and rejects any uid but the daemon owner's
  (`crates/izba-core/src/daemon/peercred.rs`, wired at
  `crates/izba-core/src/daemon/server.rs`). **Residual:** Windows AF_UNIX
  exposes no uid-equivalent peer credential; the peer-PID ioctl that does
  exist (`SIO_AF_UNIX_GETPEERPID`) is TOCTOU-prone via PID recycling, so
  izba deliberately does not trust it. There the control socket remains
  gated by directory ACLs alone; izbad now reports that mode at startup
  instead of implying enforcement. F-10 (`OpenStream` splices an unparsed
  `StreamOpen`) is narrowed but not closed — the spliced intent is still
  not authorized.
- **Repro:** code-confirmed (server.rs:192-197; transport.rs:28-40). The hello
  is read and **ignored for auth**; no `SO_PEERCRED`/`getpeereid`, no token. Sole
  gate is the 0700 daemon dir. Any process that can open the socket can
  Create/Start/Stop/Rm sandboxes, `GuestRpc`-exec inside guests, `OpenStream`-
  splice a shell into any sandbox, `PortPublish`, and `Shutdown`. **Fix:** add an
  `SO_PEERCRED` uid match (reject non-owner) as defense-in-depth even with 0700.

### F-10 — `OpenStream` splices a client-chosen, daemon-unparsed `StreamOpen` to the guest
- **Repro:** code-confirmed (server.rs:221-227). After `OpenStream{name}` the
  daemon liveness-gates the name, replies Ok, then splices raw bytes; the client
  sends an arbitrary `StreamOpen` (Attach/TcpDial/TarExtract/TarCreate) the
  daemon never inspects. F-09's peer-uid check now narrows this **on Linux**:
  only a process running as the daemon owner's uid can reach `OpenStream` at
  all, so an unrelated local user can no longer drive exec/cp/relay into any
  sandbox. It does not close F-10 — the daemon still does not parse or
  authorize the spliced `StreamOpen` itself, so any process that IS the
  daemon owner (or, on Windows, any local process at all — F-09's residual)
  can still drive exec/cp/relay into any sandbox that process can name.
  Authorization is "can you reach the socket as the right uid," not "should
  this specific request be allowed." **Fix:** parse/authorize the spliced
  intent independent of peer uid.
- **Severity re-read (2026-08-17), after F-09 closed.** On Linux the residual
  is now **same-uid only**, which is the boundary
  [the M5 vault design](../superpowers/specs/2026-08-17-m5-credential-vault-design.md)
  §10 documents as out of scope for the socket layer by construction: a process
  running as the izba owner can already read the control socket, the credential
  store, and every sandbox's state directly, so being able to drive `OpenStream`
  grants it nothing it did not already have. F-10's practical exposure on Linux
  is therefore materially lower than when it was filed, and it is **not** a
  vault prerequisite (unlike F-CRED-5, which is). It stays open because the
  stated fix — authorize the *intent*, not just the peer — is still the right
  end state and would matter under any future model where the daemon is
  reachable by more than its owner (a multi-user or remoted control plane, and
  on Windows today, where F-09 has no enforcement path). Deliberately **not**
  filed as a backlog item: an issue nobody will action is worse than an
  accurate register entry.

### F-12 — 16 MiB per-frame allocation on a length prefix before content validation (alloc-amplification DoS)
- **Repro:** code-confirmed (codec.rs:41). `read_frame` checks `len ≤ 16 MiB`
  then `vec![0u8; len]`. izbad spawns a thread per egress/control connection with
  no connection cap; N concurrent connections each force a 16 MiB alloc → memory
  exhaustion. A guest can open many vsock-1027 connections. **Fix:** per-peer
  connection ceiling + streaming/bounded reads; lower the cap per message type.

### F-13 — Unbounded thread-per-connection on guest-initiated egress
- **Repro:** code-confirmed (egress/mod.rs:159-172). The accept loop spawns an
  unbounded detached thread per vsock-1027 connection; each dials outbound and
  (MITM) registers a loopback ephemeral port. A tight connection loop exhausts
  host threads/sockets/ports. **Fix:** bounded worker pool + per-sandbox
  concurrency limit + backpressure.

### F-15 — Per-sandbox dirs and the data root created with default umask, not 0700
- **Repro:** code-confirmed (sandbox.rs:164, paths.rs:26). Only `daemon/` and
  `ca/` are explicitly 0700. The data root, `sandboxes/`, run_dir (holds
  `vsock.sock`) and logs are created under the process umask (commonly 0022 →
  world-traversable). On a multi-user host this leaks layout, console logs, and
  the control-socket path. **Fix:** chmod the whole tree 0700 consistently.

### F-17 — No decompression-bomb / file-count / total-size cap when staging+flattening OCI layers
- **Repro:** code-confirmed (image/flatten.rs:40-65). `std::io::copy(GzDecoder,
  tmp)` per layer with no ceiling; an unbounded entry count walked into an
  in-memory `BTreeMap`. A malicious image (gigabytes-of-zeros gzip, or millions
  of tiny entries) fills host disk + exhausts memory — DoS from `izba run
  <evil-image>`. **Fix:** cap decompressed size, entry count, and total bytes;
  stream rather than buffer the path map.

### F-22 — No cargo-audit / cargo-deny gate in CI
- **Repro:** code-confirmed (no `deny.toml`/`audit.toml`; no RUSTSEC step in any
  `.github/workflows`). The graph has a large net/crypto/TLS surface (reqwest,
  hyper, rustls, ring, aws-lc-rs, regorus, oci-client, vt100, portable-pty,
  vsock). A known-vulnerable transitive dep can ship silently. **Fix:** add
  `cargo-deny` (advisories + bans + licenses) + `cargo-audit` as a green-before-
  commit gate (methodology §C).

### F-23 — CA leaf certs never expire; CA omits validity window and pathlen
- **Repro:** code-confirmed (mitm.rs:65-76, 168-189). Neither CA params nor
  per-host leaves set `not_before`/`not_after`; CA is `BasicConstraints::
  Unconstrained` (no `pathlen:0`), no name-constraints, no short-lived rotation.
  If `ca.key` leaks, every guest trusting `ca.pem` accepts attacker leaves for
  **any** host indefinitely — no CRL/OCSP despite declared `CrlSign`. **Fix:**
  short leaf validity + rotation; `pathlen:0`; name-constraints to scope blast
  radius; plan revocation.

### F-28 — No hard host resource bound on the VMM + virtiofsd processes
- **Boundary:** A2 (resource exhaustion). **Repro:** code-confirmed
  (`crates/izba-core/src/procmgr/unix.rs` `spawn_detached_with_limits` — no
  cgroup membership).
- A runaway or hostile guest could exhaust host memory, file descriptors, or
  PID slots via cloud-hypervisor or virtiofsd without a hard cap.
- **Status — deferred to a cgroup follow-up (MVP-C, 2026-06-18).** `setrlimit`
  was evaluated and **deliberately not applied**: every `setrlimit` ceiling is
  per-process/per-real-uid, not per-sandbox, and breaks a confined launch.
  `RLIMIT_NPROC` is a system-wide per-uid cap on processes+threads — in the
  daemonless model the invoking user already runs hundreds of threads, so any
  usable ceiling is already exceeded and virtiofsd's `--sandbox namespace`
  sandbox-entry `fork()` dies with EAGAIN (observed on a real WSL2 host with the
  initial MVP-C build). `RLIMIT_AS` OOM-kills cloud-hypervisor, which maps the
  full guest RAM + virtiofs DAX window into its VA under `--memory shared=on`.
  `RLIMIT_NOFILE` would starve virtiofsd, which raises its own FD limit to ~1M.
  The correct per-sandbox mechanism is a cgroup (pids.max / memory.max), deferred
  to a future milestone; `ResourceLimits::for_vmm` currently applies nothing.

### F-30 — Authoritative izba state (egress policy) is invited into the guest-writable workspace
- **Boundary:** B3/B4 (egress allow-list decision integrity; the workspace
  virtiofs share is guest-RW and its in-guest "RO" is advisory). **Repro:**
  code-confirmed (commands/mod.rs:104-118; daemon/egress/mod.rs:81-108,268-273;
  sandbox.rs:659-663; izba-init/mounts.rs; cloud_hypervisor.rs:61-77).
- The live policy is **already host-only**: the CLI reads `--policy FILE`
  host-side, copies it to `<state>/sandboxes/<name>/policy.yaml`, and izbad
  enforces from that copy (start + hot-reload), **never re-reading anything in the
  guest while live**. So an agent editing a project-root `policy.yaml` does **not**
  relax a running sandbox — the headline fear is overstated. The **residual** risk
  is a design/usage footgun: (a) a human re-running `izba run --policy
  ./workspace/policy.yaml` re-reads a file the hostile guest may have rewritten
  (re-persist poisoning; worse for the multi-VM compose future where VMs share a
  project); (b) the agent can read the allow-list (probe gaps) and rewrite the
  in-repo copy to mislead a human reviewing the repo; (c) the M2 trust/ssh/oci
  shares and any future in-repo manifest/M5 vault must not regress this by
  trusting a guest-reachable path. **Crucially, "mount the control dir read-only
  *inside the guest*" is null under A1** — guest `MS_RDONLY` is advisory and
  virtiofsd (one process/share, no host RO flag) serves raw FUSE writes as the
  host user; same class as F-21. Per-subtree *host*-enforced RO needs a *separate*
  export (whole-share only) plus an RO bind-mount or a uid drop (F-29) izba lacks.
- **Fix:** (host-side, robust) pin the policy to host state with a content hash at
  apply time; never re-read a source path *under the workspace* while live;
  **warn + refuse** when `--policy` resolves inside the workspace (loud
  `--policy-allow-in-workspace` override), and require explicit re-approval on any
  change-since-trust (direnv model). Design the compose manifest + M5 vault as
  **host-only state keyed by canonical project path** (in-repo `izba.yaml` is
  *applied source*, not runtime authority); secrets must never enter any share.
  Do **not** count an in-guest RO mount as a control. Full analysis, the A/B/C
  trade-off under a hostile kernel, the virtiofs-trick enumeration, and the DX
  prior art (docker-compose / k8s / terraform / direnv / Claude Code) are in
  [policy-state-guest-isolation.md](policy-state-guest-isolation.md). Now codified
  as **invariant #9** (threat-model §7): *authoritative control-plane input is
  never read from a guest-writable path while a sandbox is live.*

- **F-16 — CA key is long-lived plaintext PKCS#8, readable by any same-user
  process; never rotates.** (ca.rs:19-73; perms 0600/0700 are correct.) Residual
  scope risk: any code as the daemon user can mint universally-trusted leaves.
  *Fix:* OS keystore / passphrase / rotation where feasible.
- **F-18 — Guest can accumulate zombie PIDs until poweroff.** (izba-init
  main.rs:172, exec.rs:64.) PID1 doesn't reap(-1) by design; guest-local DoS,

- **F-24 — CH backend does not reject commas in disk/workspace paths**
  (cloud_hypervisor.rs:86) — asymmetric with openvmm's `reject_commas()`.
  Option-injection via path contents (no shell; argv is passed directly).
  *Fix:* mirror the openvmm guard.
- **F-25 — openvmm binary pinned to an expiring (~90-day) GitHub CI artifact**
  (hack/fetch-openvmm.sh:13) rather than a signed/reproducible release. sha256
  pin is good but provenance is fragile. *Fix:* track a stable upstream release.
- **F-29 — VMM/virtiofsd run under the invoking user's uid (no per-sandbox uid
  separation).** (jail_linux.rs — no `setuid`/`newuidmap` is applied; the VMM

  launched them. A VM-escape therefore has the full invoking user's filesystem

  MVP-C:* daemonless/no-root operation makes a true uid drop infeasible without
  `newuidmap` / `install --harden`. Deferred to the userns-jailer follow-up
  milestone. Until then, the fail-closed seccomp + Landlock floor (see F-27)
  provides the main cross-filesystem containment.
- **F-31 — The `izba-trust`/`izba-ssh`/`izba-oci`/`izba-vnc` virtiofs shares
  are read-only via a guest-side mount flag only → a hostile guest kernel has
  a bounded guest→host write primitive into host state.** (mounts.rs
  `&["ro"]`→`MS_RDONLY`; cloud_hypervisor.rs:61-77 — virtiofsd v1.13.3 launched
  with no host RO flag, as the invoking host user.) The `ro` is advisory: a
  hostile kernel `remount,rw`s or issues raw `FUSE_WRITE` requests that
  virtiofsd serves, writing back into
  `<state>/sandboxes/<name>/{trust,ssh,oci,vnc}/`. **Impact is low today**
  because each share flows host→guest and tampering is self-directed (the
  guest's own CA anchor / its own sshd keys / its own crun `config.json` / its
  own VNC password hash — `izba-vnc` carries only the `kasmpasswd` HASH,
  host-authored, guest-read — all read in-guest), and virtiofsd
  `--sandbox namespace` + openat2 confines path resolution to the shared subtree
  (no escape beyond those dirs). But it is a real write primitive. *Standing rule
  (the fix until host-enforced RO exists — see
  [policy-state-guest-isolation.md](policy-state-guest-isolation.md) §6):*
  **never add a host-side reader of those directories that assumes the files are
  host-authored** — that
  would convert a benign self-write into a host-trust bug. See
  [policy-state-guest-isolation.md](policy-state-guest-isolation.md) §7.

## Mitigated on verification (would-be false positive)

- **F-26 — "Daemon name strings drive filesystem paths with no validation."**
  Downgraded: `validate_name` (`[a-z0-9][a-z0-9_.-]*`, max 64, rejects
  `..`/`/`/uppercase/leading-dot) is called at every sandbox-name entry point
  (sandbox.rs:159,362,501,514,634). Path traversal via name is **blocked**.
  Residual hardening only: validate at the protocol-dispatch layer too for
  defense-in-depth. *Kept as a record of the adversarial-verification gate
  doing its job — methodology §B.5.*
- **F-27 — cloud-hypervisor runs without Landlock filesystem confinement (on
  hosts without the Landlock LSM).** (jail_linux.rs — `Capabilities::probe()
  .landlock` gates the `--landlock` flag.) On kernels that lack the Landlock LSM
  (`CONFIG_SECURITY_LANDLOCK` absent or not listed in
  `/sys/kernel/security/lsm`), the `--landlock` flag is not passed to
  cloud-hypervisor. A CH compromise on such a host reaches the full host-user
  filesystem with no path-access restriction. **Closed by MVP-C (2026-06-18):**
  Landlock is part of the confinement **floor**; a host without it causes
  `spawn_confined` to fail closed with an actionable error unless
  `--allow-unconfined` is passed. On hosts that have Landlock, `--landlock` is
  always passed. *Residual on Landlock-less hosts:* the user must explicitly opt
  out; the degradation is visible and logged.

## Strengths worth recording (a balanced report)

- **No shell** is ever used to launch the VMM — argv passed element-by-element
  via `std::process::Command` (no shell-metachar injection).
- **PID-reuse-safe liveness** (pid + `/proc/<pid>/stat` starttime; zombies =
  dead) — genuinely well done.
- **Egress MITM fails *closed*** for enforcing sandboxes when the runtime is
  unavailable (router.rs:96-124, well-tested) — the right failure direction.
- **CA private key never enters a guest** — only the public `ca.pem` is shared
  read-only; key dir/file are 0700/0600.
- **cloud-hypervisor, virtiofsd, and the vendored static nft are sha256-pinned**
  (Alpine builder by digest, netfilter tarballs by hash).
- **Sandbox names validated** path-traversal-safe; image digests verified
  against the manifest.
